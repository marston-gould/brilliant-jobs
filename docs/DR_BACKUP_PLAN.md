## 1. Database Backup Strategy

### Supabase Managed Backups
- **Frequency:** Daily automatic (Supabase-managed)
- **Retention:** 7 days on Free tier
- **Recovery:** Via Supabase Dashboard → Settings → Database → Backups

### Critical Tables by Priority

| Priority | Table | Size | Recovery Strategy |
|----------|-------|------|-------------------|
| P0 | profiles | 304 KB | Supabase backup restore |
| P0 | user_subscriptions | 80 KB | Supabase + Stripe reconciliation |
| P0 | resumes | 64 KB | Supabase + Storage bucket |
| P1 | ats_jobs | 685 MB | Re-ingest from ATS sources (self-healing) |
| P1 | ats_companies | 4 MB | Re-scrape from source URLs |
| P1 | location_cache | 24 MB | Re-geocode on demand |
| P2 | notification_* | <1 MB | Recreate from templates |
| P2 | ref_* tables | <1 MB | Static data, version-controlled |
| P3 | seo_*, mv_* | <1 MB | Regenerated by cron jobs |

### Self-Healing Data

ats_jobs and ats_companies are **inherently recoverable** — refresh-jobs runs every 6 hours and rebuilds from ATS source APIs. Complete data loss would self-recover within 24-48 hours. location_cache rebuilds automatically as users search.

## 2. Application Recovery

### Vercel Deployment
- **Git-based:** Every deployment is a git commit — rollback via `git revert` or Vercel dashboard
- **Instant rollback:** Vercel maintains previous deployments, accessible via dashboard
- **CDN cache:** Invalidated automatically on deploy

### Recovery Procedure
1. **Identify issue:** Check console for version (BJ_VERSION), check Vercel deployment logs
2. **Rollback:** Vercel Dashboard → Deployments → click previous → Promote to Production
3. **Verify:** Check live site console for correct version number

## 4. Monitoring & Health Checks

### Database Health (run ad-hoc)
```sql
-- Full health dashboard
SELECT index_health_report();

-- Data hygiene status
SELECT * FROM hygiene_log ORDER BY ran_at DESC LIMIT 5;

-- Table sizes
SELECT tablename, pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as size
FROM pg_tables WHERE schemaname = 'public' ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC LIMIT 10;
```

## 5. Disaster Scenarios & Response

| Scenario | Detection | Recovery | RTO |
|----------|-----------|----------|-----|
| Database corruption | App errors, 500s | Supabase point-in-time restore | 1-2 hours |
| Accidental table drop | Missing data, app errors | Restore from backup | 1-2 hours |
| Bad deployment | Console errors, broken UI | Vercel rollback | 5 minutes |
| Edge Function failure | Error logs, missing notifications | Redeploy via `supabase functions deploy` | 15 minutes |
| ATS data loss | Job count drops, empty feeds | Self-heals via refresh-jobs within 24h | 24 hours |
| localStorage corruption | App won't load, blank state | `localStorage.clear()` + re-sync from cloud | 1 minute |
| Supabase outage | All API calls fail | Wait for Supabase resolution + cached data | Varies |
| GitHub outage | Can't deploy | Vercel has cached builds, can serve existing | N/A |

## 6. Error Recovery & Offline Resilience

### Client-Side Error Recovery
- `saveUserData()` catches QuotaExceededError and runs `_handleStorageFull()` emergency cleanup
- `cachedQuery()` returns stale cache on network errors (graceful degradation)
- All Supabase calls have try/catch with console logging
- User data syncs to cloud via `_flushUserData()` with 2-second debounce

### Network Failure Handling
- Saved filters, applied jobs, hidden jobs persist in localStorage (survives offline)
- Cloud sync retries on next successful connection
- IndexedDB stores resume files locally (`bj_resume_files` store)

### Data Integrity
- `data_hygiene_cleanup()` runs weekly to prevent unbounded growth
- `index_health_report()` monitors index bloat
- Automated dead job detection in refresh-jobs Edge Function
